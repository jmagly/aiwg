# Asynchronous decision jobs: offline experimental lifecycle

The AIWG-owned `DecisionJob.v1` contract validates item identities, scope, immutable pins, budgets, retention deadline, guarded transitions, and exact item-state summary counts. Jev has **no documented asynchronous job endpoint**. A job is not a provider-native bulk batch; completion does **not** authorize any downstream action.

`FileJobStore` persists immutable, mode-0600 revisions using exclusive hard-link publication and directory sync; `MemoryJobStore` supports offline fixtures. Both provide scoped acquisition and compare-and-swap. `DecisionJobRuntime` provides offline submit, read-only ordered pagination/poll, cancellation, eligible-failure requeue without dispatch, expiry reconciliation, tombstoning and scoped legal-hold toggles that reject deletion while held. `OfflineJobWorker` fences an individual fixture attempt durably before invoking an explicitly supplied test executor; a thrown, aborted or invalid fixture result becomes execution-unknown. Its callback is **not** an admitted backend provider integration. Restart reconciliation never replays a fenced attempt; finalization retries only a bounded compare-and-swap after concurrent sibling completion, never the executor. Different item subjects are presented separately. The caller must derive the full scope from trusted authentication, **not** model input; the runtime compares the authenticated scope before submit or transition. Other scopes receive no job record. A duplicate job ID with unchanged identity returns the existing snapshot; changed pinned identity is rejected. Tombstones prevent ID reuse. An expired running item with a dispatched attempt becomes `execution-unknown`, never cleanly canceled. Retry of unknown items is forbidden by the contract. Out-of-order completions preserve original item order. All offline operations are disabled from provider-facing CLI/API surfaces.

An explicit host-only `admittedJobItemExecutor` bridge composes the existing synchronous evaluator with a durable D03 receipt store and enabled scheduler policy. It rejects unbound principal/workspace, missing cost limits, changed ruleset/definition/binding/input digests and incomplete receipts before exposing an item reference. Same-subject native batches remain within one item invocation. This bridge is not exposed through CLI/API. The worker requires an explicit durable token/cost reservation for admitted evaluator callbacks, sums reservations across all sibling item attempts under the job CAS, and refuses dispatch that exceeds the pinned job budget; the bridge also rejects plans whose host estimates exceed that fence. Reservations are conservative and not refunds. `accountDecisionJob` reads the scoped D03 and D04 receipts to report known token/cost totals, unknown usage, labeled estimates and budget exceedance; it ignores per-answer allocations in native batches and rejects cross-item shared-state ownership. This report is read-only and **not** a transactional pre-dispatch quota reservation; a host must not enable jobs just because these pieces exist.

**Do not expose this runtime to users yet.** There is no job-level provider scheduler or aggregate quota/fairness enforcement, rate limits, retry policy integration, retained-result byte accounting, protected payload store, D10 backup/physical erasure integration (the scoped legal-hold flag blocks local tombstoning but is not a complete D10 policy), complete D14 OpenTelemetry golden traces (metadata-only job lifecycle spans exist), or full crash/load qualification. The journal retains digest-only historical metadata after tombstoning; it does not persist raw inputs or results. Do not store PII or secrets in IDs, scope fields, errors, or fingerprints. Retention expiry currently changes lifecycle state but does not prune the journal. File stores require a local filesystem supporting atomic hard links; they do not provide a distributed CAS. No claim of exactly-once provider billing or execution is made.

Different item subjects must never be merged into a shared-state request; eligible same-subject question batching belongs inside a single item and its existing admission and receipt flow. Before enabling jobs, bind execution to D03/D04 receipt ownership and D10/D14 controls, add non-guessable handles, and qualify isolation, recovery, saturation and accounting under offline tests. Until then this remains an offline foundation, not a production asynchronous jobs feature.
