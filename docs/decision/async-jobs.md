# Asynchronous decision jobs: offline experimental lifecycle

The AIWG-owned `DecisionJob.v1` contract validates item identities, scope, immutable pins, budgets, retention deadline, guarded transitions, and exact item-state summary counts. Jev has **no documented asynchronous job endpoint**. A job is not a provider-native bulk batch; completion does **not** authorize any downstream action.

`FileJobStore` persists immutable, mode-0600 revisions using exclusive hard-link publication and directory sync; `MemoryJobStore` supports offline fixtures. Both provide scoped acquisition and compare-and-swap. `DecisionJobRuntime` provides offline submit, read-only ordered pagination/poll, cancellation, eligible-failure requeue without dispatch, expiry reconciliation, and tombstoning. The caller must derive the full scope from trusted authentication, **not** model input; the runtime compares the authenticated scope before submit or transition. Other scopes receive no job record. A duplicate job ID with unchanged identity returns the existing snapshot; changed pinned identity is rejected. Tombstones prevent ID reuse. An expired running item with a dispatched attempt becomes `execution-unknown`, never cleanly canceled. Retry of unknown items is forbidden by the contract. Out-of-order completions preserve original item order. All offline operations are disabled from provider-facing CLI/API surfaces.

**Do not enable provider dispatch or expose this runtime to users yet.** There is no admission-controlled scheduler, bound provider callback, quota/fairness enforcement, rate limits, retry policy integration, retained-result byte accounting, protected payload store, D10 backup/legal-hold/physical erasure integration, complete D14 OpenTelemetry golden traces (metadata-only job lifecycle spans exist), or full crash/load qualification. The journal retains digest-only historical metadata after tombstoning; it does not persist raw inputs or results. Do not store PII or secrets in IDs, scope fields, errors, or fingerprints. Retention expiry currently changes lifecycle state but does not prune the journal. File stores require a local filesystem supporting atomic hard links; they do not provide a distributed CAS. No claim of exactly-once provider billing or execution is made.

Different item subjects must never be merged into a shared-state request; eligible same-subject question batching belongs inside a single item and its existing admission and receipt flow. Before enabling jobs, bind execution to D03/D04 receipt ownership and D10/D14 controls, add non-guessable handles, and qualify isolation, recovery, saturation and accounting under offline tests. Until then this remains an offline foundation, not a production asynchronous jobs feature.
